# Визуализатор графа зависимостей npm-пакетов (вариант 15)

Практическая работа №2 по дисциплине «Конфигурационное управление».
Консольное приложение (CLI) на Python для анализа и визуализации графа
зависимостей пакетов JavaScript (npm). Готовые менеджеры пакетов и
библиотеки для получения зависимостей не используются.

Текущий этап — **Этап 5. Визуализация**: приложение строит граф
зависимостей пакета с учётом транзитивности, исключает пакеты по
подстроке фильтра, находит циклические зависимости, выводит порядок
загрузки и граф: текстом на языке Mermaid, изображением SVG или
ASCII-деревом. Результаты сравниваются с работой npm. По флагу
`--reverse` выводятся обратные зависимости.

| Этап | Что выводит приложение |
|------|------------------------|
| 1 | параметры в формате `ключ=значение` |
| 2 | прямые зависимости пакета |
| 3 | граф зависимостей и найденные циклы |
| 4 | порядок загрузки зависимостей и найденные циклы; с `--reverse` — обратные зависимости |
| 5 | порядок загрузки, циклы и граф (Mermaid или ASCII-дерево), изображение SVG |

Каждый этап хранится в своей ветке (`stage-1` … `stage-5`) и слит в
`main`.

## Структура проекта

```
src/depgraph/
    __main__.py   точка входа (python -m depgraph)
    config.py     параметры командной строки и их проверка
    registry.py   запрос метаданных пакета к реестру npm
    repo_file.py  чтение тестового репозитория из файла
    graph.py      построение графа (DFS без рекурсии), порядок загрузки

```

## Параметры

| Опция | Обязательная | Описание |
|-------|--------------|----------|
| `--package ИМЯ` | да | имя анализируемого пакета |
| `--repo URL_ИЛИ_ПУТЬ` | да | URL репозитория пакетов или, в тестовом режиме, путь к файлу тестового репозитория |
| `--test-mode` | нет | работать с тестовым репозиторием из файла |
| `--ascii-tree` | нет | выводить зависимости ASCII-деревом вместо текста Mermaid |
| `--filter ПОДСТРОКА` | нет | не учитывать пакеты, имя которых содержит подстроку |
| `--image ФАЙЛ.svg` | нет | сохранить изображение графа в файл SVG |
| `--reverse` | нет | вывести обратные зависимости: какие пакеты зависят от данного (только с `--test-mode`) |

### Проверка параметров

| Параметр | Правило |
|----------|---------|
| `--package` | непустое; в обычном режиме — имя по правилам npm: маленькие буквы, цифры, `-`, `.`, `_`, `~`, не начинается с `.` или `_`, допускается область видимости `@scope/имя`, не длиннее 214 символов; в тестовом режиме — только большие латинские буквы (`A`, `B`, `AB`) |
| `--repo` | непустое; в обычном режиме — URL со схемой `http` или `https` и адресом сервера; в тестовом режиме — путь к существующему файлу |
| `--test-mode`, `--ascii-tree`, `--reverse` | флаги, значений не принимают |
| `--reverse` | только вместе с `--test-mode` |
| `--filter` | непустая подстрока без пробелов |
| `--image` | имя файла с расширением `.svg`; папка, в которой он создаётся, должна существовать |

## Сбор данных

Метаданные пакета запрашиваются модулем `urllib.request` из
стандартной библиотеки по адресу `{repo}/{имя}`, например
`https://registry.npmjs.org/express`. В имени с областью видимости
косая черта кодируется: `@babel/core` → `@babel%2Fcore`.

Запрос отправляется с заголовком
`Accept: application/vnd.npm.install-v1+json`. Реестр тогда отдаёт
сокращённые метаданные без README и описаний: для крупных пакетов
это сотни килобайт вместо десятков мегабайт. Из ответа берётся:

- версия из `dist-tags.latest`;
- поле `dependencies` этой версии: имя зависимости и диапазон версий.

`devDependencies`, `peerDependencies` и `optionalDependencies` не
учитываются. Каждый пакет в графе представлен один раз, в версии
`latest`; диапазоны версий из `dependencies` не разрешаются.
Расхождения с npm — в разделе «Сравнение с npm». Зависимости из реестра
обходятся по алфавиту.

Ошибки получения данных выводятся в поток ошибок, код завершения 1:

| Ситуация | Сообщение |
|----------|-----------|
| пакета нет в реестре (HTTP 404) | `depgraph: error: package not found: 'имя'` |
| другой ответ HTTP | `depgraph: error: HTTP error 500 Internal Server Error for URL` |
| сервер недоступен | `depgraph: error: cannot connect to URL: причина` |
| истекло время ожидания (15 с) | `depgraph: error: timed out while reading URL` |
| ответ не JSON | `depgraph: error: invalid JSON in response from URL` |
| нет версии `latest` | `depgraph: error: no 'latest' version for 'имя'` |
| версии `latest` нет в `versions` | `depgraph: error: version X of 'имя' is missing in metadata` |
| строка файла без двоеточия | `depgraph: error: ФАЙЛ:N: expected 'NAME: DEPENDENCIES'` |
| неверное имя в файле | `depgraph: error: ФАЙЛ:N: invalid package name 'a'` |
| пакет описан дважды | `depgraph: error: ФАЙЛ:N: package 'A' is defined twice` |
| пакета нет в файле | `depgraph: error: package not found in test repository: 'Z'` |
| не удалось получить изображение | `depgraph: error: cannot render image: причина` |
| не удалось записать файл изображения | `depgraph: error: cannot write 'ФАЙЛ': причина` |

## Тестовый репозиторий

В тестовом режиме (`--test-mode`) граф читается из файла, реестр не
нужен. Каждая строка: имя пакета, двоеточие и прямые зависимости
через пробел. Имена — большие латинские буквы, пустые строки
пропускаются. Пакет, который указан как зависимость, но не описан
отдельной строкой, считается пакетом без зависимостей. Анализируемый
пакет (`--package`) в файле описан быть обязан.

| Файл | Что показывает |
|------|----------------|
| `repos/simple.txt` | общая зависимость (ромб): `D` нужен и `B`, и `C` |
| `repos/cycle.txt` | цикл `A -> B -> C -> A` |
| `repos/filter.txt` | фильтр: `--filter TEST` убирает `TESTLIB` вместе с тем, что нужно только ему |
| `repos/broken.txt` | ошибка формата файла |

`repos/simple.txt`:

```
A: B C
B: D
C: D
D:
```

## Построение графа

Граф строится обходом в глубину (DFS) без рекурсии (`graph.py`,
функция `build_graph`): вместо стека вызовов используется список, в
котором для каждого открытого пакета хранится итератор по его
зависимостям. Поэтому глубина графа не ограничена лимитом рекурсии
Python; это проверяет тест с цепочкой вдвое длиннее этого лимита. Зависимости
каждого пакета запрашиваются один раз, даже если пакет нужен
нескольким другим.

Фильтр `--filter` исключает пакет, если его имя содержит подстроку
(с учётом регистра). Исключённый пакет не обходится, поэтому его
зависимости попадают в граф только если нужны другим пакетам.
Анализируемый пакет фильтром не исключается.

Каждый пакет при обходе находится в одном из состояний: не встречен,
открыт (сейчас на пути от корня) или обработан. Если зависимость
указывает на открытый пакет, это цикл: обход по такому ребру не
продолжается, цикл выводится строкой `Cycle: ...`, а ребро остаётся в
графе. Если зависимость указывает на уже обработанный пакет, это не
цикл, а общая зависимость.

## Порядок загрузки

Порядок загрузки (`graph.py`, функция `load_order`) — это порядок, в
котором пакеты заканчивают обход в глубину (тоже без рекурсии): пакет
попадает в список только после всех своих зависимостей, анализируемый
пакет — последний. Так устроена установка: пакет можно поставить и
запустить его скрипты, когда уже стоят пакеты, от которых он зависит.

Если в графе есть цикл, требование «после всех зависимостей»
выполнить нельзя. Ребро, замыкающее цикл, пропускается: пакет, на
котором цикл замкнулся, оказывается после остальных пакетов цикла.

Пакеты из реестра выводятся с версией, после списка выводятся
найденные циклы.

## Обратные зависимости

Обратные зависимости пакета — это пакеты, которые от него зависят,
напрямую или через другие пакеты. С флагом `--reverse` программа
читает тестовый файл, разворачивает в нём все рёбра («от зависимости к
зависящему пакету», функция `reverse_dependencies` в `repo_file.py`) и
обходит полученный граф тем же DFS без рекурсии (`build_graph`).
Поэтому фильтр и поиск циклов работают так же, как для прямых
зависимостей.

Порядок загрузки, Mermaid и изображение для обратных зависимостей не
выводятся. Каждая строка вывода: пакет и стрелка `<-` к пакетам, которые от него
зависят напрямую. `(none)` — от пакета никто не зависит.

```
$ sh run.sh --package D --repo repos/simple.txt --test-mode --reverse
Reverse dependencies of D (dependents: 3):
  D <- B, C
  B <- A
  A <- (none)
  C <- A
```

От `D` зависят `B` и `C` напрямую и `A` через них.

Флаг работает только в тестовом режиме. Реестр npm хранит для
пакета только его собственные зависимости; списка пакетов, которые от
него зависят, в реестре нет. Чтобы найти их, пришлось бы скачать
метаданные всех пакетов npm (их миллионы), а сторонние сервисы для
этого задание использовать не разрешает.

## Сравнение с npm

Сравнение делает скрипт `sh scripts/compare_npm.sh ИМЯ` (нужен
Node.js с npm). Он выводит порядок загрузки приложения, затем ставит
пакет командой `npm install` во временную папку и показывает, в каком
порядке npm обращался к реестру, и дерево `npm ls --all`.

Результат для пакета `accepts` (ноябрь 2026, npm 10.9.7):

| depgraph | npm: запросы метаданных | npm: скачанные архивы |
|----------|-------------------------|-----------------------|
| 1. mime-db@1.54.0 | accepts | mime-db-1.52.0.tgz |
| 2. mime-types@3.0.2 | mime-types | accepts-1.3.8.tgz |
| 3. content-type@3.1.1 | negotiator | mime-types-2.1.35.tgz |
| 4. negotiator@1.1.0 | mime-db | negotiator-0.6.3.tgz |
| 5. accepts@1.3.8 | | |

Расхождения и их причины:

1. **Версии и состав пакетов.** `accepts@1.3.8` требует
   `mime-types ~2.1.34` и `negotiator 0.6.3`. npm выбирает наибольшую
   версию, подходящую под диапазон: `mime-types@2.1.35`, которому
   нужен `mime-db@1.52.0`. Приложение для каждого пакета берёт
   `latest`: `mime-types@3.0.2` и `negotiator@1.1.0`, а у последнего
   есть зависимость `content-type`, которой у npm в дереве нет. Поэтому
   у приложения 5 пакетов, у npm 4.
2. **Порядок запросов.** npm читает метаданные по уровням дерева
   (в ширину): сначала `accepts`, затем обе его зависимости, затем
   `mime-db`. Приложение обходит граф в глубину.
3. **Порядок скачивания.** npm скачивает и распаковывает архивы
   параллельно, порядок их завершения меняется от запуска к запуску:
   в примере `accepts` скачан раньше своих зависимостей. Строгого
   порядка «зависимости раньше» npm придерживается при запуске
   скриптов установки (`preinstall`, `install`, `postinstall`), и
   именно его показывает приложение.
4. **Несколько версий одного пакета.** npm может поставить две версии
   одного пакета в разные папки `node_modules`, если диапазоны не
   пересекаются. В графе приложения у каждого имени один узел.
5. **Виды зависимостей.** npm 7+ сам ставит `peerDependencies` и
   пытается поставить `optionalDependencies`; приложение их не
   учитывает.
6. **Циклы.** npm ставит все пакеты цикла, порядок скриптов внутри
   цикла не определён. Приложение тоже включает их все, отбросив одно
   ребро цикла.


## Визуализация

После порядка загрузки выводится граф (`render.py`). По умолчанию —
текст на языке Mermaid. Узлы получают идентификаторы `n1`, `n2`, … в
порядке обхода, а имя пакета записывается подписью в кавычках: имена
npm содержат `@`, `/` и `.`, которые нельзя использовать в
идентификаторах Mermaid. Текст можно вставить в https://mermaid.live
или в Markdown на GitHub, где он отрисуется картинкой.

С флагом `--ascii-tree` вместо текста Mermaid выводится дерево (тоже
обходом без рекурсии). Пакет, у которого есть зависимости и который
уже показан выше, помечается `(see above)` и повторно не раскрывается.
Ребро, замыкающее цикл, помечается `(cycle)`.

С опцией `--image ФАЙЛ.svg` текст Mermaid кодируется в base64 и
отправляется в сервис https://mermaid.ink, который возвращает
изображение SVG; оно сохраняется в файл. Для этого нужен интернет,
даже в тестовом режиме.

### Примеры для трёх пакетов

Скрипт `sh scripts/demo_stage5.sh` создаёт в папке `examples/` для
пакетов `debug`, `accepts` и `body-parser` текст Mermaid (`.mmd`),
изображение (`.svg`) и вывод с ASCII-деревом (`.txt`). Файлы
`*-npm.txt` — вывод `npm ls --all` после `npm install` того же пакета
(ноябрь 2026, npm 10.9.7).

| Пакет | Пакетов в графе | Пакетов у npm | Файлы |
|-------|-----------------|---------------|-------|
| `debug` | 2 | 2 | `debug.mmd`, `debug.svg`, `debug.txt`, `debug-npm.txt` |
| `accepts` | 5 | 4 | `accepts.mmd`, `accepts.svg`, `accepts.txt`, `accepts-npm.txt` |
| `body-parser` | 36 | 40 | `body-parser.mmd`, `body-parser.svg`, `body-parser.txt`, `body-parser-npm.txt` |

Версии и состав зависимостей зависят от момента запуска: реестр
отдаёт текущую версию `latest`.

### Сравнение с npm ls

Дерево `accepts` у приложения и у `npm ls --all`:

```
accepts@1.3.8                     accepts@1.3.8
├── mime-types@3.0.2              ├─┬ mime-types@2.1.35
│   └── mime-db@1.54.0            │ └── mime-db@1.52.0
└── negotiator@1.1.0              └── negotiator@0.6.3
    └── content-type@3.1.1
```

Расхождения и их причины:

1. **Версии.** Как и в порядке загрузки, `npm ls` показывает версии,
   которые npm выбрал по диапазонам (`mime-types ~2.1.34` →
   `2.1.35`), а приложение — `latest` (`3.0.2`). У другой версии могут
   быть другие зависимости: у `negotiator@1.1.0` есть `content-type`,
   у `negotiator@0.6.3` зависимостей нет. Для `body-parser` это даёт
   разницу в пакетах: например, он требует `content-type ^2.1.0`,
   `raw-body ^3.0.2`, `type-is ^2.1.0`, и npm ставит `2.1.0`, `3.0.2`,
   `2.1.0`, а приложение берёт `3.1.1`, `4.0.0`, `3.0.0`. Итог: 40
   пакетов у npm и 36 у приложения.
2. **Повторы.** `npm ls` показывает пакет, который уже встречался,
   с пометкой `deduped` (в `body-parser-npm.txt` таких строк 25).
   Приложение пишет `(see above)` и только для пакетов с
   зависимостями, а лист выводит заново без пометки.
3. **Расположение, а не зависимости.** `npm ls` строит дерево по
   папкам `node_modules`: при нескольких версиях одного пакета
   вложенная копия показывается внутри того пакета, которому она
   нужна. Приложение строит дерево по зависимостям, у каждого имени
   один узел.
4. **Корень.** `npm ls` выводит проект, в который пакет поставлен
   (`npm-example@1.0.0`), приложение — сам пакет.
5. **Виды зависимостей.** `npm ls --all` показывает и установленные
   `peerDependencies` и `optionalDependencies`, приложение — только
   `dependencies`.
6. **Изображение.** Штатного средства для картинки графа у npm нет;
   Mermaid и SVG — возможность только приложения.

## Сборка и запуск

Требуется Python 3.8+, сторонние библиотеки не нужны.

```sh
sh run.sh --package ИМЯ --repo URL [--test-mode] [--ascii-tree] [--filter ПОДСТРОКА] [--image ФАЙЛ.svg] [--reverse]
run.bat --package ИМЯ --repo URL ...      # Windows
```

Запуск тестов:

```sh
sh test.sh        # Linux / macOS
test.bat          # Windows
```

Демонстрация:

```sh
sh scripts/demo_ok.sh       # корректные запуски
sh scripts/demo_errors.sh   # ошибки для каждого параметра
sh scripts/demo_stage2.sh   # Этап 2: данные из реестра и файла, ошибки
sh scripts/demo_stage3.sh   # Этап 3: ромб, цикл, фильтр, реестр npm
sh scripts/demo_stage4.sh   # Этап 4: порядок загрузки, обратные зависимости
sh scripts/demo_stage5.sh   # Этап 5: визуализация, примеры в examples/
```
